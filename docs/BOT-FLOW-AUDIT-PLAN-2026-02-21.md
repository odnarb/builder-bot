## Executive Summary
The current bot flow is close to the documented roadmap, but there are several correctness and control-path gaps. The most critical issue is that mixed action plans (`move_to` + placements) are not preserved end-to-end in chat build execution.

## Findings

### P0 - Mixed action plans are broken in chat build flow
- Evidence:
  - `apps/bot/command-router.js:349` offsets all steps through `offsetStructure(...)`.
  - `apps/shared-utils/offsetStructure.js:1` only returns `{ x, y, z, block }`, dropping `type`, `target`, `distance`.
  - Mixed-action support is expected by schema conversion in `apps/shared-utils/instruction-schema.js:188`.
- Impact:
  - `move_to`/`follow`/`stop` actions generated by AI are lost or malformed before execution.
  - Contradicts documented “mixed action plans” completion.

### P0 - Commander auth check allows non-commander chat control
- Evidence:
  - `apps/bot/index.js:92` only checks whether commander UUID exists in `bot.players`, not whether `username` matches commander UUID.
- Impact:
  - Any player can issue `@Bot ...` commands while commander is online.

### P0 - Web UI follow/come-here path is effectively broken
- Evidence:
  - `apps/bot/ws-server.js:100` calls `handlePlayerCommand` with hardcoded `username: 'Commander'`.
  - `apps/bot/command-router.js:166` resolves follow target via `bot.players[username]?.entity`.
- Impact:
  - UI follow/come-here commands cannot resolve a real player entity in common setups.

### P1 - Tier enforcement drift from canonical policy
- Evidence:
  - Bot-local limits in `apps/bot/command-router.js:22` diverge from canonical policy in `apps/api/config/tier-policy.js:61`.
  - Admin local cap is `Infinity` in `apps/bot/command-router.js:39`, canonical cap is `6000` in `apps/api/config/tier-policy.js:93`.
  - `pending` tier from API can bypass bot-local checks (`apps/api/index.js:649`, `apps/bot/index.js:58`, `apps/bot/command-router.js:122`).
- Impact:
  - Inconsistent behavior/messages between bot and backend policy.

### P1 - Build completion and success semantics are inaccurate
- Evidence:
  - `apps/bot/execute-commands.js:147-150` treats “already correct block” as `false`.
  - `apps/bot/execute-commands.js:92-94` marks any `false` placement as build failure.
  - `apps/bot/execute-commands.js:102` always announces “Build complete!” even on failures.
- Impact:
  - Incorrect success status and noisy/faulty user feedback.

### P1 - WebSocket input type mismatch (`raw_prompt`)
- Evidence:
  - `apps/webui/src/components/PromptInput.jsx:17` sends `{ type: 'raw_prompt' }`.
  - `apps/bot/ws-server.js` has no `raw_prompt` route.
- Impact:
  - User prompt submissions silently drop unless they match chat command prefixes.

### P1 - Command concurrency guard is disabled
- Evidence:
  - `apps/bot/index.js:20-21` declares guard.
  - `apps/bot/index.js:108-117` has guard logic commented out.
- Impact:
  - Overlapping build commands can race inventory clearing, movement, and execution state.

### P2 - API tier trust model weak for unauthenticated build calls (cross-surface)
- Evidence:
  - `apps/api/index.js:1586` build endpoint has no `jwtCheck`.
  - `apps/api/index.js:1595` tier is taken from request body and normalized.
- Impact:
  - Tier can be client-selected when unauthenticated, which conflicts with strict monetization assumptions in docs.

## Remediation Plan

## Phase 1 (P0): Correctness and Control Safety
1. Replace `offsetStructure` usage in chat build path with an action-aware transformer.
2. Preserve action type payloads (`move_to`, `follow`, `stop`) and only offset coordinate-bearing actions.
3. Fix commander authorization in chat handler to validate sender UUID matches configured commander UUID.
4. Resolve actual player identity for WS chat commands (derive from commander UUID or explicit username in payload).

Acceptance criteria:
- Mixed plans containing both movement and placement execute without dropping non-placement actions.
- Only commander-originated chat can trigger bot command routing.
- Web UI follow/come-here works against active commander entity.

## Phase 2 (P1): Policy Consistency and UX Reliability
1. Align bot-side limits with canonical tier policy (`maxBlocksPerBuild`, prompt constraints strategy).
2. Normalize unsupported tiers (for example `pending`) to safe runtime behavior (`free`).
3. Fix `executeCommands` result semantics:
   - “already correct” should not count as failure.
   - completion message should reflect success vs partial failure.
4. Add `raw_prompt` WS routing or remove that client branch and return explicit unsupported-message feedback.
5. Reinstate single-flight command handling (or lightweight queue) for build commands.

Acceptance criteria:
- Bot and API produce consistent tier-limit behavior and user-facing messaging.
- Build status persisted to backend matches actual outcome.
- Prompt input path never silently drops user actions.
- Concurrent command spam does not corrupt bot execution state.

## Phase 3 (P2): Hardening and Observability
1. Add bot-focused tests for:
   - action-aware offset transformation,
   - commander auth routing,
   - WS message routing (`chat_command`, `raw_prompt`, `instruction_plan`).
2. Add structured command lifecycle logging (`queued`, `started`, `finished`, `failed`) for easier incident debugging.
3. Coordinate API-side tier-auth hardening (bind tier to authenticated user when auth is present, tighten unauth behavior).

Acceptance criteria:
- New regression tests catch mixed-action regression and commander bypass attempts.
- Logs provide end-to-end traceability per command/build.
- Tier/economics path is no longer client-tier-driven for authenticated usage.

## Suggested Execution Order
1. Phase 1 (P0) in one focused PR.
2. Phase 2 (P1) as a second PR.
3. Phase 3 (P2) as a third hardening PR.
